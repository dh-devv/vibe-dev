# 초기 아이디어 v2: 미루기 재판소 (검증 전 초안)

> 상태: 초안. 다른 모델의 검증을 거친 뒤 `PRD.md`로 확정한다.
> v1(일정 플래너)은 흔한 구조라 폐기한다. 이 문서가 최신이다.

## 1. 한 줄 정의

**"미루고 있는 일을 법정에 세운다. AI 변호인과 검사가 서로의 주장에 반박하며 공방을 벌이고, 판사는 그 공방 전체를 읽은 뒤 이 사건에 맞는 최적의 방안을 판결한다."**

## 2. 왜 새로운가

| 기존 앱 | 미루기 재판소 |
| --- | --- |
| 할 일을 목록으로 정리한다 | 미루는 **이유**를 다룬다 |
| 일정을 대신 짜 준다 | 사용자가 "미루고 싶은 마음"을 직접 변론한다 |
| 알림과 압박으로 몰아붙인다 | 양측 공방을 지켜보며 스스로 상황을 객관화한다 |
| 누구에게나 같은 조언을 한다 | 공방에서 드러난 원인에 따라 **사건마다 다른 판결**을 내린다 |

미루기의 원인은 시간 부족, 막막함, 완벽주의, 흥미 상실, 감정 회피 등 사람과 사건마다 다르다. 이 앱은 변호인(마음의 이유)과 검사(미룰 때의 비용)가 맞붙게 해 원인을 드러내고, 판사가 그 공방을 근거로 맞춤 방안을 낸다.

## 3. 대상과 문제

| 항목 | 내용 |
| --- | --- |
| 대상 | 과제·보고서·취업 준비를 자꾸 미루는 대학생과 직장인 |
| 문제 | 해야 할 일을 알면서도 **시작하지 못해** 마감 직전에 몰린다 |
| 효과 | 시작까지 걸리는 시간 단축, 원인에 맞는 해결책 확보 |
| 측정 | 판결 이행률, 사건 접수 후 첫 행동까지의 시간 (앱 안에서 표시) |

## 4. 사용 흐름 (MVP)

1. **사건 접수**: "보고서를 3일째 안 쓰고 있다"처럼 입력. 마감일, 중요도, 미루는 이유는 선택 입력.
2. **공판**: 변호인이 변론하고, 검사가 반박하고, 변호인이 재반박한다(최대 2라운드). 실제 주고받은 발언을 스트리밍으로 보여 준다.
3. **판결**: 판사가 공방 전체를 읽고 **판결문**을 낸다. 판결문은 다음으로 구성한다.
   - 쟁점 요약: 양측 주장 중 무엇을 받아들였고 무엇을 기각했는지
   - 원인 진단 유형: 막막함, 완벽주의, 흥미 상실, 시간 부족, 피로 등 (확정 진단이 아닌 추정으로 표시)
   - **처방**: 사건에 맞는 방안 1~3개. 방식은 사건마다 다르다. 예: 일을 쪼개기, 시간 박스, 마감 앞당기기, 일부 위임·포기, 환경 바꾸기, 보상 설계, 쉬고 나서 하기
   - 집행 계획: 언제 무엇을 할지
   - 판단 근거: 어느 발언을 근거로 삼았는지 인용
4. **사용자 선택**: 판결을 **수용 / 항소(새 주장 추가 후 재심) / 기각**한다. 저장과 타이머는 수용한 판결만 해당한다.
5. **집행**: 처방별 체크리스트와 타이머로 이행을 기록한다. 이행하면 "집행 완료" 기록이 쌓인다.
6. 로그인 없이 바로 쓰는 데모 모드를 제공한다. 심사 에이전트가 접근할 수 없으면 전 항목이 1점이다.

## 5. 멀티 에이전트 설계 (Microsoft Agent Framework)

| 에이전트 | 역할 | 하지 말아야 할 일 | 도구 |
| --- | --- | --- | --- |
| 변호인 | 미루고 싶은 마음의 이유를 공감하며 변론하고, 검사의 반박에 재반박 | 일을 하지 말라고 권유, 사실 날조 | 없음 |
| 검사 | 변호인의 주장을 반박하고 미룰 때의 실제 비용(남은 시간, 누적 지연)을 제시 | 비난, 협박, 사실 과장 | MCP: 현재 시각·마감 계산 |
| 판사 | 공방 전체를 읽고 쟁점을 정리해 **사건에 맞는 방안**을 판결. 근거 발언을 인용 | 공방에 없는 사실 추가, 의료·심리 진단, 고정된 한 가지 처방 반복 | 없음 |
| 서기관(검토) | 판결이 공방에 근거하는지, 실행 가능한지, 입력 속 지시문(프롬프트 인젝션)이 없는지 점검 | 새 판결 작성 | 없음 |
| 집행관 | 수용된 판결을 체크리스트·타이머·기록으로 저장 | 승인 없이 저장 | MCP: 타이머·기록 |

- 순서: `변호인 → 검사 → 변호인(재반박) → 검사(최종 의견) → 판사 → 서기관`. 라운드 수는 최대 2회로 제한한다.
- 변호인과 검사는 서로의 발언을 컨텍스트로 받아 실제로 맞받아친다. 판사는 두 발언 기록 전체를 입력으로 받는다.
- 서기관이 반려하면 판사가 1회 다시 판결한다.
- 항소 시 사용자의 새 주장을 추가해 공판을 이어서 진행하고 판사가 재판결한다(컨텍스트 유지).
- **GitHub Copilot SDK**는 모델 연결, **Agent Framework**는 에이전트·워크플로·도구 호출·스트리밍을 맡는다.

## 6. 책임 있는 AI 원칙

- 모든 발언에 "AI가 생성한 내용" 표시를 붙인다.
- 의료·상담 서비스가 아님을 화면에 밝힌다. 위기 신호(자해 등)가 보이면 공판을 중단하고 전문 기관 안내를 한다.
- 저장은 사용자의 수용 후에만 한다.
- 입력은 저장 최소화하고, 비밀 정보는 Key Vault·Managed Identity로 관리한다.

## 7. 기술 방향 (쉬운 스택)

| 영역 | 선택 | 이유 |
| --- | --- | --- |
| 언어 | Python 3.12 | 이미 설치됨, 두 SDK 모두 지원 (`github-copilot-sdk`, `agent-framework`) |
| API | FastAPI + SSE | 공판 진행을 실시간 전달 |
| UI | 정적 HTML/CSS/JS, 반응형 | 빌드 불필요, 법정 대화 연출에 적합 |
| 저장소 | Azure Table Storage 또는 Cosmos DB (후보) | 사건·판결 기록에 충분 |
| 도구 서버 | MCP 서버(Python): 시각·마감 계산, 타이머·기록 | 도구 호출 깊이 확보 |
| 배포 | Azure Container Apps | 규정이 허용하는 기본 도메인 |
| 보안·관찰성 | Managed Identity, Key Vault, Application Insights | Azure 통합·신뢰 항목 |
| 실행·배포 도구 | Aspire(우선), 대안은 `azd` + Docker Compose | 한 번에 실행·추적·배포 |

## 8. 평가 기준 대응

| 기준 (가중치) | 대응 |
| --- | --- |
| Copilot SDK + Agent Framework (25%) | 5개 에이전트의 역할 분담, 공방 대화를 판사가 읽는 컨텍스트 처리, 반려 루프, MCP 도구 호출, 스트리밍, 항소 시 컨텍스트 재사용 |
| 생산성·문제 적합성 (18%) | "시작 못 함"이라는 구체적 문제, 시작 시간·이행률 지표 |

| 기능 완성도 (16%) | 접수→공판→판결→수용/항소→집행 전 과정, 오류·재시도 |
| UX (12%) | 연극 같은 진행 표시, 사용자 통제(수용·항소·기각), 접근성, 반응형 |
| 책임 있는 AI (6%) | AI 표시, 승인 후 저장, 인젝션 방어, 위기 신호 처리 |
| 혁신성 (5%) | 적대적 공방에서 맞춤 처방을 도출하는 방식, 비난 없는 설득 |

## 9. 위험과 대응

| 위험 | 대응 |
| --- | --- |
| 콘셉트가 가벼워 보임 | 지표와 근거(미루기 원인별 대응 원리)를 PRD에 명시 |
