# TDD: 기술 결정 기록

결정마다 이유, 버린 대안, 감수하는 단점을 적는다.

| # | 결정 | 이유 | 버린 대안 | 감수하는 단점 |
| --- | --- | --- | --- | --- |
| 1 | 주제는 "미루기 재판소" | 원인별 맞춤 처방을 공방으로 끌어내는 방식은 흔하지 않고, 멀티 에이전트가 꼭 필요하다 | 일정 플래너 | 가벼워 보일 수 있다. 지표와 안전 장치로 보완한다 |
| 2 | 판결은 사건마다 다른 처방 | 서비스의 다양성과 활용 깊이를 높인다 | "5분 행동" 고정 | 품질 편차. 검증기와 예시 사건으로 관리한다 |
| 3 | Python 3.12 | 설치되어 있고 두 SDK 모두 지원한다. 학습 비용이 낮다 | .NET, Node.js | Aspire 자료가 .NET보다 적다 |
| 4 | `GitHubCopilotAgent`로 연결 | 두 필수 기술(25%)을 한 경로에서 쓴다 | 모델 API 직접 호출 | 새 패키지라 자료가 적다. 13:00에 먼저 검증한다 |
| 5 | 에이전트 3개 + 코드 검증기 | 에이전트 수보다 활용 깊이를 본다. 검증은 코드가 더 정확하고 빠르다 | 5개 에이전트 | 모델 기반 검토는 만들지 않는다 |
| 6 | 공방은 3발언(변호→검사→재반박) | 호출 4회로 지연과 쿼터를 줄이면서 "맞받아침"을 보인다 | 5발언 2라운드 | 공방이 짧다 |
| 7 | 도구는 함수로 시작, MCP는 P1 | MCP 서버 분리는 서비스가 하나 늘어 일정 위험이 크다. 도구 호출은 함수로도 증명된다 | 처음부터 MCP | MCP 시연이 늦어지거나 빠질 수 있다 |
| 8 | 배포는 `azd` + Dockerfile, Aspire는 선택 | `azd`는 Python과 Container Apps에서 검증된 경로다. Aspire는 .NET 설치와 Python 서비스 설정 학습이 필요해 4시간 일정에 위험하다 | Aspire 우선, Docker Compose | Aspire의 통합 실행·추적 이점을 포기한다. 시간이 남으면 시도한다 |
| 9 | 앱 1개(API + 정적 UI) | 리소스와 배포 단계를 줄이고 형식적 서비스 감점을 피한다 | API·UI 분리 | 확장성은 낮다. 이 규모에서는 문제없다 |
| 10 | 기록은 `localStorage` | 서버에 개인정보를 두지 않고 DB가 필요 없다 | Cosmos DB, Table Storage | 기기를 바꾸면 기록이 없다 |
| 11 | 정적 HTML/CSS/JS | 빌드가 없고 팀원 누구나 고칠 수 있다 | React, Blazor | 복잡한 상태 관리는 어렵다. 화면이 단순해 문제없다 |
| 12 | SSE 스트리밍 | 단방향이라 쉽고, 공방을 실시간으로 보여 준다 | WebSocket | 양방향 불가. 필요 없다 |
| 13 | 로그인 없이 공개, 요청 제한 | 심사 에이전트가 자격 증명 없이 써야 한다. 불가능하면 전 항목 1점이다 | 로그인 | 남용 위험. 빈도·일일 상한·복제본 1개로 대응한다 |
| 14 | Container Apps 비밀로 토큰 주입 | Key Vault 연동보다 빠르고 코드에 비밀이 남지 않는다 | Key Vault 참조 | 감사·순환 기능이 약하다. 시간이 남으면 Key Vault로 옮긴다 |
| 15 | 위기 신호는 키워드 코드로 검사 | 빠르고 결정적이며 모델 호출을 쓰지 않는다 | 모델 분류 | 놓치는 표현이 있을 수 있다. 면책 문구를 함께 둔다 |
